## Payment and accounting trace

### Enumeration and frontend selection

1. `backend/internal/payment/types.go` defines `TypeWooshPay`; `GetBasePaymentType` and the provider registry/factory retain it.
2. Payment configuration validation, protected-field handling, enabled-instance loading, and `GetAvailableMethodLimits` retain WooshPay. Its provider advertises the `wooshpay` supported type, so it reaches the checkout response.
3. `frontend/src/types/payment.ts`, `PaymentMethodSelector.vue`, `SettingsView.vue`, and both locale files retain the type, selector option, icon, and administrator configuration. `PaymentView.vue` filters the server-provided methods and opens the WooshPay checkout in the current tab, covered by `PaymentView.spec.ts`.

### Order creation and currency conversion

1. `POST /api/v1/payment/orders` reaches `PaymentService.CreateOrder`, which validates the plan/provider, re-resolves the selected provider instance/currency, and persists its ID, key, and sanitized snapshot.
2. Balance recharge credits use decimal multiplication and round to two balance decimals; configuration persistence uses `formatPositiveFloatExact`, avoiding binary-float truncation of the recharge multiplier.
3. Direct CNY subscription checkout calculates the gateway amount in currency precision while `calculateSubscriptionOrderAmountUSD` stores `payment_orders.amount` in USD. `pay_amount` remains the gateway-currency amount.
4. The subscription daily limit uses the stored USD order amount. Balance-order limits use the credited balance amount. This preserves Aox's USD comparison basis.
5. WooshPay accepts only CNY, validates the configured HTTPS API host, converts to minor units, supplies a stable order/idempotency reference, and returns its hosted checkout URL.

### Callback, fulfillment, and affiliate calculation

1. WooshPay callbacks enter `/api/v1/payment/webhook/wooshpay`. The provider validates event JSON, timestamp, HMAC signature, merchant order identity, currency, and amount.
2. `HandlePaymentNotification` resolves the pinned provider instance/snapshot, compares the paid amount with `pay_amount` using currency-aware tolerance, performs the paid-state transition atomically, and uses a fulfillment lease/idempotency guard.
3. Balance fulfillment credits `order.Amount`; subscription fulfillment assigns the subscription. `affiliateRebateBaseAmount` uses `order.Amount`, so both recharge and subscription affiliate calculations remain USD-based even when the gateway was paid in CNY.
4. Query reconciliation uses the provider's payment-intent/order reference and persists the gateway trade number.

### Refunds

The official v0.1.171 `require_force` behavior is accepted. `PrepareRefund` blocks unavailable providers, calculates the gateway refund with currency precision, and returns `RequireForce` when the balance/subscription deduction cannot be completed. The admin API/UI explicitly confirms and retries with force; execution keeps deduction, provider refund, status, rollback, and audit transitions coordinated. WooshPay intentionally reports refund as unsupported, and its provider-instance refund flag remains the availability gate.

Existing focused tests cover provider creation/signatures/callbacks, amount mismatch and duplicate fulfillment, CNY-to-USD conversion, multiplier precision, USD affiliate/daily-limit bases, currency-aware refunds, and updater restrictions. No additional production-contract test was needed beyond the valid one-line mock isolation fix.

## Version and managed-update invariants

`backend/cmd/server/VERSION` being `0.1.182` at official tag v0.1.183 is expected: the official release workflow injects the release tag into built artifacts. Aox's `build-aox.yml` validates its `x.y.z-aox.A.B.C` candidate tag and injects both `VERSION` and `BUILD_TYPE=aox`; the root and deploy Dockerfiles carry that metadata into the binary.

For `BUILD_TYPE=aox`, backend update checks do not contact the upstream release service and managed update, rollback listing, and rollback execution return `ErrAoxManagedUpdateDisabled`. The frontend also hides/skips those actions for Aox builds. The official rollback test was accepted because it does not weaken this build-type gate. No upstream write, push, PR, candidate image build/publish, or deployment was performed during this review.

## Review concern fixed

`GroupsView.columnSettings.spec.ts` reset every hoisted API mock except `getLiveCapability`. Because queued one-shot results and call history can leak between tests, this was a valid isolation concern. `beforeEach` now calls `getLiveCapability.mockReset()`. The focused suite passes all 7 tests.
