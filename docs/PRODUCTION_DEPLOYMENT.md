## Deployment procedure

1. Connect using the SSH command above. In the deployment directory, check the running application version/image, container health and free disk space.
2. Confirm the target release and immutable image digest, then pull that digest before interrupting service.
3. Create a dated backup directory under backups/ with restrictive permissions; preserve docker-compose.yml and .env. Do not commit environment files, credentials or database backups.
4. Stop only the sub2api service and confirm no other database clients are writing. Dump the sub2api database using pg_dump -U sub2api -d sub2api -Fc through the postgres service. Verify the dump is nonempty, validate its catalog using pg_restore --list, and record its SHA-256 checksum. Restore into an isolated database and verify recovery before recreating the application; never restore over the live database as part of validation.
5. Update the image in the base Compose, preserve diagnostics, networks and secret file references, and validate with `docker compose -p sub2api -f docker-compose.yml config --quiet`. Keep the compatibility override empty. Recreate only the application with `docker compose -p sub2api -f docker-compose.yml up -d --no-deps --no-build --force-recreate sub2api`.
6. Check container health, /app/sub2api -version, restart count, startup/migration errors, and the public endpoints above.
7. Current .31-to-.30 rollback restores the latest saved Compose and recreates only sub2api. There are no new migrations; rollback changes only the image and does not restore the database. Keep Clash and diagnostics enabled and preserve Nginx log protection and payment settings. Retain all existing migration records and data. For historical .25-to-.24 rollback, follow [the assignment-aware rollback gates](AOX25_DEPLOYMENT_PLAN.md#6-回退与新功能使用边界): inspect all assigned proxies, including soft-deleted rows, and their bindings/backup references before changing the image. The initial deployment used zero assignments; later assignments invalidate that assumption. Retain migration 246 and its constraints; do not automatically clear assignments or restore an old database. Historical .24-to-.23 rollback uses [the cache rollback plan](AOX24_DEPLOYMENT_PLAN.md) and both files from the same successful .24 backup; its old base alone pins .22.
8. Update this document with the verified version, digest, previous image and backup location.

When using a deployment script, upload it with scp and execute the remote file. Do not pipe a script into bash over SSH: Docker commands may consume the script's standard input.

## Rollback stop rule and checker requirements

1. Each user authorization covers one deployment attempt only. Any automatic rollback ends that authorization, including a rollback caused by a false alarm in a checker script.
2. Stop immediately once the rollback version is healthy. Do not stop service again, redeploy, or modify production configuration. Only read-only investigation is permitted: verify rollback-version health, migration records and data state, and determine the root cause.
3. Report the timeline, interruption duration and affected request count, root cause and supporting evidence, proposed fix, and recommended retry window to the user. Redeployment requires new, explicit user authorization; retrying under the same authorization is not permitted.
4. Migration checksum checks must match `backend/internal/repository/migrations_runner.go`: apply `strings.TrimSpace` to the file content, then compute SHA256, or read the recorded checksums directly from `schema_migrations` and compare them with the verified runner-compatible values. Never use a hash of the raw file bytes as the migration checksum. For example, in .30, `246_enable_gemini_image_generation_groups.sql` has raw-file SHA256 `f49b458cfbd52bd17f5bb02e30e3813c8e192e4ae38bce6358713ef65f3874b5` (`f49b458c…`), but its runner checksum is `87267be7ab657173768989e2b0b105c5569c5930a7f1ed124f4cf81e5198297c`.
5. New or modified deployment checker logic must pass validation in an isolated environment before it is used in a production window.
6. Latency checks must use non-overlapping windows, counting each request in only one window. For releases that change only frontend files or documentation, latency is warning-only and does not trigger rollback. Preserve all other hard rollback conditions and report warnings, model/effort sample counts, p50/p95, token averages and account distributions.
7. Drain using read-only Redis gateway concurrency slots, not TCP connection counts. Snapshot the unexpired request members in numeric account and live-account slot keys at drain start; wait only for that initial set to disappear or expire under the configured slot TTL (live: 60 seconds). New members do not extend the wait. An empty initial set passes immediately; timeout remains 180 seconds and must stop the attempt before stopping service. Record release time and the final total in-flight count, including new requests. New arrivals, requests exceeding slot TTL and paths without slots may still be interrupted by the application's five-second shutdown; report actual impact. Preflight failures, drain timeouts and invocation errors also end authorization; do not rerun the executor under it.
8. For a verified migration-free release, explicit user approval may permit online `pg_dump -Fc` instead of the stopped-service dump in step 4. Complete isolated restore validation before drain and image replacement. Compare restored table row counts with the dump's own data, not a production database that is still accepting writes; verify schema, roles/permissions, indexes, constraints and table count. Record the authorized deviation. An online backup predates the switch and must never be restored automatically during image rollback.
